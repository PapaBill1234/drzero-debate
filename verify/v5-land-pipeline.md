## D22: seed base strict data from the lander

The defect is real. Every land moves main. The next card that checks on that main finds no base dir, so it runs `gate_fast.sh` on a fresh clone and then `strict_all` (`cardrun.py:1024-1031`). I compared the lander's `full-<build_rev>/strict/*.json` with `bases/<pushed head>-b489a5c2ab30/strict/*.json` for pod-01, wmain-01, cg-02, merge-01 and merge-02. All 25 files are byte-equal. The base of b6aea91 (a `Docs/Plan` commit) is byte-equal to the base of its parent e3765f9. The build and strict tools do not read `Docs/**` (grep of bns-lift `tools/`, `CMakeLists.txt`; only `parity.sh` reads `Docs/Parity` for its rc). The step data confirms 6 fresh base builds (145.9, 75.9, 221.0, 60.8, 122.6, 84.1 s) and 3 lock waits (75.4, 25.7, 28.2 s). Only 230 s is on the land chain for certain. Build hook A and hook B. Add the digest check: `strict_all` keeps an old valid JSON file (`cardrun.py:773`), so the seed must compare the strict `tool_digest` that `s_strict` recorded with the current one. Skip the shadow-mode fresh build. Use a one-time cmp canary instead (the 25/25 result already exists). Tests in `tests/test_cardrun.py` with `cardrun_stubs.py`: (1) a land with an accept-only delta writes `done` with `seeded_from`, and the next card's `base_build` is `reused` with no `full_build` stub call; (2) a delta with a `src/` path gives no seed; (3) a digest mismatch gives no seed; (4) an invalid JSON gives no seed; (5) a seed exception leaves the land exit 0 and `landed`; (6) hook B seeds from a docs-only first-parent ancestor. Coordinate the stamp format with D04.

## D23: accept commits build-neutral

The conflict with `parity.sh` is real but harmless for safety. `parity.sh` reads `Docs/Parity/baseline/<exe>.json`, `allow-worse.txt` and `excluded.tsv` only to set its rc. The funcdiff and strict outputs do not depend on them. Proof R1 (`proof.py:141-152`) and `lost_check` read the baseline of the new base again, because their keys hold `base` (`cardrun.py:1382-1389`). R1 is stricter than `parity.sh`: it does not waive `allow-worse` and it counts gone names. So a rebuild for a baseline-only delta adds no safety. But the item has no hits. In all recorded cardrun states (8 distinct rebases), no card had a delta from its build base that touched only `Docs/Parity` and README. A waiting card always gets the lander's source commits plus the accept commit. Docs-only moves outside `Docs/Parity` (b6aea91) are already build-neutral in `s_plan`. The author `--reset` path (`author.py:1339-1347`) also keeps the old build for them, because `full-<rev>` and the base dir stay on disk and `review.run` carries receipts by bundle digest. The 640 s figure of run2-31 is mostly base-build time (146 s, 84 s: that is D22) plus merge-train time (D24). The only real use is a stacked build (D24). It also needs a `proof.py` R8 edit at line 244, which changes the checker digest and rebuilds every card in flight once (D07 splits that digest).

## D24: merge train

The idea is sound, but the measured gain on the land chain is 0 s. The judge of run2-37 and run2-31 found that the queued cards' commits were written after the previous land, so no speculative build could start earlier. It saves slot time (about 1,314 slot-s, plausible), not wall time. It needs the D23 path rule, a pinned `proof.py` change (R8 build binding with `spec_parent`), a spec mode in cardrun, landq rebase logic and remote slots. cardrun does not send `full_build` through slotq today (`cardrun.py:150`), so the remote slots it would use are idle. Trigger to revisit: a wave where 2 or more cards are `ready` in the land queue while the front card lands.

## D25: early_review after full_build

The defect is real and the 435 s claim holds (437 s measured over 6 reject runs). But most of each gap is `base_build` time (pod-02 60.8 s, pod-01 213.5 s, lock waits of 25.7 and 28.2 s). D22 removes that time. After D22 only `strict` (2-21 s) and `proof` (under 3 s) remain, about 55 s per wave. The claim "a reject saves the later review tokens" is wrong: the review runs once in both orders. The proposal also reviews all new funcdiff MATCH keys before the strict data exists. That adds model draws for items that would get auto credit (strict full and cfg). If it is built later, compute the item set from the candidate strict data and `judge_exe` (no base needed), and reuse the existing carry (`receipts.local_carry_source`, `receipts.py:376`): no new carry code is needed. Build D22 first, then measure again.

## Q8: does an early review change the verdict?

No. The bundle (`review.py:826-830`) holds the build images, the lift source of the symbol at the rev, and the Hex-Rays text. It does not hold the proof base or the base strict data. In the data, the same bundle digests occur under 4 proofs with 3 different bases (merge-03 on e3765f9, merge-03b on b6aea91, merge-03c and merge-03d), and `review.run` carried them without a new draw (`review.py:833-840`). So an early D0 receipt is carried to the final proof with the same verdict. Each bundle still gets exactly 1 draw, the same as today. The 1.6 % flip rate (5 of 322 draw pairs, run2 judge notes) applies equally in both orders. The early review does not add or remove flip exposure. Two limits: an item set that differs from the final proof adds draws (tokens) but changes no final verdict; a D0 transport park is not carriable (`receipts.py:365-373`), so that item is drawn again at the end.

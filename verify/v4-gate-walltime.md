## D19
The defect is real. `gate_fast.sh:76` runs `buildcache.py gc` after every build, and the build command does not end until gc ends. In 66 builds gc removed 0 entries. The store holds 3.85 GB against a 32.2 GB limit and grows about 1.4 GB per work day. So gc does no work today. The tail is 1.2 s at p50. But 4 of 66 builds had a cold walk: 25 s (11-25 22:20), 114 s (01:10), 617 s and 921 s (14:02-14:18). Each one came after an idle gap and a low dentry count (see Q1). The 921 s tail was on the land path. Build the 6 h stamp form in the gate. It also covers the remote stores. An operator-tick form does not reach remote hosts. Two traps: the remote run script holds the slot lock on fd 9 and reads the job over ssh. The background job must close fd 9 and detach stdin/stdout/stderr, else the remote slot stays busy (exit 75) and ssh waits for gc. Do not use `ionice -c3`: the sdb scheduler is mq-deadline, so idle class has no effect. Use `nice`. Side fact: `store_max_bytes` (32.2 GB) is larger than the free space on /data (18 GB). gc cannot protect the disk; only `disk_guard.py` does.

## D20
Part 1 (early restore) is real and safe. `vs_restore` reads the repo sources, the namespace index and the store. It needs nothing from `tools/gate.sh`. `build.sh:62-69` checks the object age only against the source, its `.dep` headers and `build.sh`. A restore that starts before `wine_setup` also walks an empty `build/`, so its own walk is shorter. Restore was shorter than `gate_sh` in 58 of 62 runs. The gain is 761 s over 62 runs, about 3 s at p50 and up to 113 s per build. Part 3 (index self-heal) fixes a real code gap, but I found 0 orphan entries in the indexed namespaces. It is 4 lines, so add it. Part 2 (detached record tail, `gate.rc` before record) gives little: record p50 is 0.8 s. An early `gate.rc` alone gives 0 s, because cardrun waits for the process to exit. A detached tail races three `rmtree` calls in cardrun and the next remote job on the same slot. It also escapes the time limit. Do not build part 2.

## D21
The tail after ninja is real and large: p50 80 s, sum 2,461 s over 30 v2b builds (70 % of `gate_sh`). Only the resym step has a cache, and it keys on mtime. The clang cc cache already proves that about 98 % of TUs are unchanged per card (p50 8 misses of 391). So a layout cache keyed on the cc key has a high hit rate. The remaining tail (parse, selftest, resym) is about 10 s ❓; the solver split was not re-run. Build the cache first. The defer part adds risk for a small gain after the cache: a card rev with the old `gate.sh` runs `gate_extra` inline, so a deferred copy runs it twice. pdb_layout also takes all 8 cores while `parity_sh` links. Decide on defer only after D37 measures the tail that is left. D05 (agent A) changes the same lines (`gate.sh:15`, `pdb_layout.json`, PDB sha), so D21 must come after D05. The resym sha key is a correctness fix and belongs in D05. Correction to the master row: a `gate_fast.sh` change does not rebuild the base. It changes `checker_digest` (`proof.py:63-65`), so each live card reruns `full_build` once.

## Q1 (cause of the 14:02-14:18 stall)
Logs and timestamps only. No cache drop, no gc run.
1. The host was not frozen. sar wrote its 14:10:01 sample on time. sdb did 256 tps in 14:10-14:20. The Dr. Zero run1 agents finished 9 calls in 14:07-14:18 (`run1/calls.jsonl`). An engine worktree wrote files at 14:10-14:14 (`eng-wt/r3-multiexe`). So a SIGSTOP or a VM pause is not the cause.
2. No other build ran. The store `events.jsonl` has 0 events from 14:07 to 14:18. gc takes no lock, so the two walks did not wait on each other through a lock.
3. Memory pressure evicted the dentry and inode cache. `dentunusd` fell from 709k (13:50) to 188k (14:10). `inode-nr` fell from 1.08M to 614k. kswapd scanned 5-7k pages/s. Free memory was 238 MB at 13:40.
4. sdb was at its IOPS ceiling: about 260 tps, queue 28-34, await 105-124 ms, iowait 53-59 %. One synchronous metadata read then costs about 0.12 s. 7,700 reads give 921 s.
5. The same end (3 ms apart) fits a convoy. Both walks read the same tree in the same order (9,154 and 9,156 entries). The later walk ran through the pages that the first walk had loaded, caught up, and then both waited on the same reads. When the last read ended, both ended.
6. The pattern repeats: the 114 s tail (01:10) had `dentunusd` 119k-126k; the 25 s tail (22:20) had a drop from 851k to 599k. Fast tails (14:28 onward) had 0.6-1.9M.
Conclusion: a cold metadata walk on an IOPS-capped disk under memory pressure. Evidence: plausible, strong. Not proven per I/O ❓. The other sdb load at that time (queue about 30) was probably the Dr. Zero run1 agents and other sessions ❓. D19 removes the symptom from the build path. Any other full walk of the store or a clone during a wave can meet the same stall.

## Q7 (sdb at 100 % util)
Confirmed and refined. sdb and sda are both "QEMU HARDDISK" with rotational=1. That flag is a virtual-disk default; it does not prove an HDD. The real limit is an IOPS ceiling on sdb: tps stays at 250-290 in every busy sample, for request sizes from 12 to 90 kB and throughput from 1.7 to 21 MB/s. sda in the same VM reached 1,077 tps at 0.5-1.7 ms await and 3-6 % util. sdb also saturated with no build running (11:40-12:40, reads only, 200-245 tps). Swap is on sda (`/swapfile`), so swap is not the sdb load. Cheapest test: move the build store (3.85 GB live) and the cardrun work dirs to sda (53 GB free) by config, run one wave, and compare sar and `gate.phases`. Old store namespaces hold 3,729 unindexed entries that no restore uses; they can stay on sdb.

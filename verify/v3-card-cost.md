## Reasons

**D15.** The core claim is true. I re-ran the baseline diff. d67687a → 6824f3d: 207 DIFF, 55 DIFF→MATCH, 3 new keys (+58). 6824f3d → 3c8e78c: 152 DIFF, 7 DIFF→MATCH, 8 new keys (+15). 145 DIFF stay open, and `unmatchable.md` has 148 "Proof level" rows. So every open item has tries ≥ 1. The E = c/p rule with the seed p = 0.056 drops all of them. D14 (agent B) drops proof A/B rows already, so the E rule adds nothing for this pool. The hook in `plan_cards.gains()` is wrong: that function scores new LobbyDaemon bodies, not DIFF repairs. The fitted p(cause, band, tries) table has too few positives (7) to fit. Keep the cheap part: a `tries` field and yield per tries class in the wave report. Add the E rule only when a later pool gives n ≥ 10 positives per class. The cross-exe "lead pattern card" part belongs to D32 (agent C).

**D16.** The gap exists, but the evidence goes against the fix. I counted tool calls whose input names the item RVA or PDB name. In all 11 v2b author.py sessions, no item passes 8 calls in one session. So with that count, the cap never fires and saves about 0. With the wider map of run2-41 (D40), MATCH items need more calls than DIFF items (median 16 against 9), and N = 8 cuts 4 of 6 MATCH. The 2 "author MATCH" items of pod-01 are also not clean: `operator delete[]` got 3-4 named calls, and `wmain` needed the lead commit f8f975a. A stop also forces a fresh session with a 15-36k token start prompt. Build D40 (`turns.py`) first. Decide a budget only from its data.

**D17.** Most of it is done. All v2b author cards ran through `author.py` (state.json `opts` and commit messages "author round 1 (author.py)"). The 100k split and the result-JSON trim landed in 46f88dfb. The 25-30 % gain was measured on run1 ad-hoc subagents. The v2b author.py sessions have a mean prompt of 17-70k tokens and a peak above 100k in only 3 sessions. The open part is the item table in the split handoff. It saves about 67-72k units for each split (pod-01 x01, plausible). v2b had 1 split. Note: `runcard.sh` now sets `--ctx-split 160000` and `mkcard.py:98` says 160,000, so splits get rarer. Build the reduced table (edited / not touched) after D13. Skip the "examined N calls" column: it needs the full call list in the meter.

**D18.** In author.py sessions, the waste that run2-03 measured does not occur. run2-03 measured ad-hoc subagents (0 "Author run:" lines). In the 11 author.py sessions I found 0 `sleep`, build, gate or `buildonce` calls and 1 Bash result over 8000 chars. So the measured gain is about 0. The Hex-Rays deny is harmful today: every v2b card ran with `packet: false`, and the card rule tells the author to read the hr file (97 calls did). Keep only the wait deny entries as a cheap guard. They cost 5 lines and cannot change MATCH counting. Drop hr from `ADD_DIRS` only for packet cards. Leave `BASH_OUTPUT_CHARS` at 16000 or set 8000. Both are fine; the gain is about 500 tokens a wave.

**T5.** Done. The split, the author.py route and the result-JSON trim are in the code. The item-state table (D17) is the only open part.

**T6.** Done in 46f88dfb. The meter takes the output count from `message_delta`. A `result` line cannot trip the cap. Tests exist.

**Q3.** 84k is a fair bar only for a fresh pool. The manual wave reached it on 207 untried items with a 26.6 % yield. The v2b pool held the 152 survivors of that wave, and the yield fell to 4.6 %. At the manual cost per pool item (4.89M / 207 = 23.6k, measured), the survivor pool needs about 513k per DIFF→MATCH, or about 239k per MATCH when new keys count (plausible). v2b paid 181k (2.72M / 15) or 186.5k with all actors. So v2b did not lose to the manual process on this pool. The comparison was unfair. Use 84k only for tries = 0 pools (for example LobbyDaemon new bodies or a new exe). For retried pools, report tokens per attempt and yield per tries class (D39 and the small D15).
